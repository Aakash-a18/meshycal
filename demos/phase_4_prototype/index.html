i · the trust layer

Three primitives.
One signed receipt.

Mesherra is the trust layer underneath. MeshyCal is the first thing built on top. Together they make agent-to-agent interaction tessera-grade: the two halves either fit, or they don't.

I

Provenance

Every interaction produces two signed entries — one per ledger. A hash chain links them. You can re-open the books years later and prove what happened.

Identity

Scoped disclosure

iii · the user's constitution

A user-signed rulebook.
No one else can write it.

Every principal carries a tiny signed document — their constitution. It names exactly which payload fields may leave, and which may not. The airlock obeys it because the user signed it.

The default MeshyCal template

When you install MeshyCal, this rulebook is offered and signed with your key. You can edit it — the editor is coming in Phase 4 — but the defaults express a sensible posture for scheduling agents.

The block list closes the leakage attacks people instinctively fear: calendar titles, attendee emails. The allow list says what crosses: candidate slots, duration, soft timezone hints.

field: mesherra.policy/doc-v1
stored: per-principal SQLite, Ed25519-signed
verified: on every read by the bound public key 

principal_id: "iris@meshycal.demo"
version: 1
issued_at: "2026-05-24T12:00:00Z"
rules:
  # meshycal proposals — what leaves
  - match:
      schema: "meshycal.scheduling/proposal-v1"
      direction: outbound
    outbound_allow:
      - candidates
      - duration_minutes
      - constraint_hints
    outbound_block:
      - calendar_titles
      - attendee_emails
    max_array_size:
      candidates: 5

  # meshycal proposals — what is allowed in
  - match:
      schema: "meshycal.scheduling/proposal-v1"
      direction: inbound
    inbound_allow:
      - candidates
      - duration_minutes
      - constraint_hints
iv · what's next

Three scenarios.
Increasing agentic complexity.

Scenario one runs in the browser above. Two and three need new backend capability — multi-party orchestration first, then agent-to-agent reasoning.

i.

Two-party direct request

A asks B for an appointment. The airlock strips the rich payload. Both sides sign matching receipts. Tessera fit.

backend: complete. Phase 3 covers this scenario fully.

live in this prototype
ii.

Four-party group negotiation

A, B, C, D find a common time. The orchestration is no longer request-response — it's a coordinator pattern. Whoever convenes drives the protocol; the trust layer scopes each bilateral exchange.

backend needed: multi-party SDK extension on top of Mesherra's two-party primitive. Mesherra's policy + receipts apply per-bilateral with no change.

next backend slice
iii.

Cascading reschedule

A asks B for a slot B has with C. B's agent reasons about tradeoffs and negotiates with C's agent to free the slot. Two delegation chains, three signed exchanges.

backend needed: LLM-driven scheduling agent + per-user policy governing what the agent may propose autonomously. The trust layer is unchanged — only the agent gets smarter.

after scenario ii
The metaphor

In Roman antiquity, two parties broke a clay or bone tile — a tessera — in half. Each kept one. Descendants centuries later who had never met could fit the halves together and prove the original bond by the precision of the fit.

Mesherra is the digital tessera. Trust holds without anyone trusting anyone in advance: the two halves either fit, or they don't.

— after centuries, a fit.
The repos

Mesherra — the trust layer (Python). Provenance, identity, scoped disclosure.

MeshyCal — the first Delegation. Domain-specific scheduling agent + this UI.

Both repos depend strictly downstream: MeshyCal imports Mesherra, never the reverse.
